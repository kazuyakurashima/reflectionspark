# 提出の概要の下書き

- **何の文書か**：提出フォームの設問「プロジェクト概要：解決する課題と、誰のためのものか」に入れる文の下書き（日本語）。
- **フォームの指定**：1 文目は「このプロジェクトは、〔誰〕の〔課題〕を〔どう変える〕〔形〕です。」。その下に、具体的な利用の場面を含めて 500 字以内。
- **語り**：動画の冒頭、README の「なぜ作ったか」、`docs/なぜ作るか.md` と同じ話にする。
- **言えることの範囲**：評価で言えるのは、作ったダミーで、設計した条件にどれだけ応えるかまで。成長は目指す姿として書き、このアプリの効果として書かない。
- **数字**：入れていない。入れるときは `eval/results/runs/report.md` と同じ版（正解 v1・評価スクリプト v1）の数字にする。
- **長さ**：空白と改行を除いて数えた。

## 案 1（おすすめ）

このプロジェクトは、塾の講師やコーチの「分かっているのに、次の面談で変えられない」という課題を、自分の発言を根拠に振り返り、次に試す一つの行動を自分で選び、次の面談で確かめる流れに変える Web アプリです。

作り手は塾で 20 年面談を続け、アプリを作る前に普通の AI との対話で「今回 3 回目の指摘になります」と言われて、気づくだけでは直らないと知りました。

たとえば講師が生徒面談の後に、ボイスメモの文字起こしを貼ります。Claude が話者を付け、本人が確かめます。自分の点と一言を先に付けると、よく表れた所と次に試せる所が、原文と一致した引用と問いで返ってきます。AI の読みは本人が開くまで閉じています。問いへの答えから「もし（場面）なら、（行動）する」の候補が出て、講師は一つを選びます。次の面談では自己評価を先に付け、AI はそれを見ずに読み、前回の行動が現れたかを引用つきで返します。人を採点せず、決めるのは本人です。設計の骨は、文献を格付けした根拠マップに基づきます。目指すのは、他者の可能性を引き出す人が自分の可能性に気づき、自ら選び直せるようになることです。

## 書き方の注意

- 1 文目で、面談する側が自分の面談を振り返る道具だと分かるようにする。「AI に相談できる」「チャットで質問」とは書かない。
- 「成長する」「上達する」「改善が証明された」と効果として書かない。「目指す」と書くのはよい。
- 「ナッジ」「HITOTSU」は使わない。「Spark」は画面 3 の行動の名前にだけ使う。
- 「覚えている」「記録する」「メモリ」は、記録係と夢が公開 URL につながるまで書かない。
- 実話は、アプリを作る前に普通の AI との対話で起きたことだと分かるように書く。面談の中身は書かない。
