# 記録係と夢の最小の実証（検証用・暫定）

- **何か**：ダミーの面談 6 本（同じ講師の 3 組）を今のエンジンで分析し、記録係（Managed Agents のセッション）にメモリストアへ 1 回 1 ファイルで書かせ、夢（Dreams）を Sonnet 5.5 で 1 回回し、夢の出力の根拠を発話の原文と照合した記録。設計は `docs/設計書.md` の工程 5・6 と「覚えていると整理」。
- **どこまで言えるか**：動く検証用のプロトタイプまで。記録係と夢が最後まで動き、夢の引用が原文と一致した、というところまでで、振り返りの質が良くなるかと、夢の仮説が妥当かは確かめていない。公開デモ（公開 URL）にはつないでいない。
- **扱い**：このフォルダの中身はすべて「検証用・暫定」。分析も夢の出力も、本人（作り手）は確かめていない。確かめた分析として画面や README に出さない。Demo Mode、localStorage、本番のメモリストアには入れていない（メモリストアは検証用の名前で別に作った）。
- **金額と ID**：このフォルダには書かない。時間とトークン数だけ。

## 回し方

```
node scripts/memory/run.mts analyze
node scripts/memory/run.mts record  --state <リポジトリの外のファイル> --session-cap-minor <セッション 1 本の上限> [--names-file <名前の一覧>]
node scripts/memory/run.mts record  --state <同じファイル> --verify-only   # ストアを読むだけで確かめる（書き換えない。LLM は呼ばない）
node scripts/memory/run.mts dream   --state <同じファイル> --cap <入力トークン換算の上限>
node scripts/memory/run.mts correct --state <同じファイル> --interview <面談> --old <直す文> --new <直した文>
node scripts/memory/run.mts verify  --state <同じファイル>
node scripts/memory/run.mts summary --state <同じファイル>
```

`record --dry-run` は API を呼ばず、記録の文だけを作る。Node 22 では `--experimental-strip-types` を付ける。記録の形を変えて比べるとき（`--no-scores`・`--no-reading`）は、同じストアに混ぜないよう新しい `--state` にする。

## 記録の形

コードの今の形（`record_format: 2`）は、見出しで出所を分ける。

| 見出し | 入るもの | 出所 |
|---|---|---|
| 原文 | 照合済みの引用、アプリが発話番号から取った前後の発話（「>」の行） | 発話の本文。どの発話を選んだかは AI |
| 行動 | 決めた行動、前回の行動、基準、決まり方 | この実証では検証用に置いたもの |
| AI が書いた説明と判定 | 文脈、観察、直後の相手の反応、追跡の判定 | AI。原文と照合していない |
| その回の AI の読み（仮説） | 読み、意図した選択として見たとき、追跡のなぜの一文、項目ごとの点 | AI |

- **この回（2026-11-06T00-53-41）の記録は前の形。** 「事実」の見出しに、AI の観察・反応・追跡の判定が混ざっていた。誤りなので形を直したが、新しい形ではまだ記録係と夢を回していない（`record --dry-run` で文を作って確かめただけ）。この回の出力は前の形から作られたもの。
- **読みと点を記録に入れるか**は決めていない。設計書は記録係に点と判定も渡すと決めている。夢は「点を根拠にしていない」と書いたが、それだけでは影響が無いとは言えない。読みごと外す（`--no-reading`）・点だけ外す（`--no-scores`）で夢の出力を比べるまで、結論を出さない。
- 回をまたいだ変化は記録に書かない。記録係は索引に 1 行足すだけ。

## 止める条件と、止める処理

- **保存の検査で止める。** 読み返した文が渡した文と違えばアプリが書き直し、もう一度確かめる。それでも違う、索引の行が無い、性質の言葉か名前がある、セッションにエラーがあれば、済みにせず、そこで止める。再実行は、済みの面談だけを飛ばす。夢は、6 本すべてと索引が済みのときだけ始める。
- **費用の止め方は厳密な上限ではない。** 記録係のセッションには API の budget を渡し、時間切れのときは止める要求も送る（要求が通ることと、そこで止まることは別）。夢には上限の設定が無いので、使用量を定期的に見て、超えたら取り消す。見る間隔と取り消しにかかる時間の分は超える。状態を続けて読めないときは、取り消しを頼んで見張りをやめ、終わりを確かめていないと分かる形で返す。これらはテストの偽物で確かめただけで、実際の超過や通信エラーでは試していない。

### 誤りと、弱い所

仮説は夢の出力のまま残し、手で直していない。読んで見つけた問題をここに書く（Claude とレビューで読んだ。本人は確かめていない）。

- **H4 の反例は反例になっていない。** 仮説の文は「発話は短かった」。反例の欄の「2時間ですか」「やってみます。」は短いままで、欄の見出しは「『はい』でなかった発話」に変わっている。何を反例とするかが途中で変わった。しかも `student-seiseki-2` の発話 111・113 は根拠にも入っている。
- **H4 は条件の違う場面を混ぜている。** 仮説の文は「どれかを含む」で、時刻と時間の量まで決めた案（発話 110）も、いつ・どの範囲が決まっていない案（`student-seiseki` の発話 72）も同じ扱いになっている。
- **H3 は形の違う場面をまとめている。** 「家だとなかなか」のような状況の話と、「えっと」「そうかもしれないです。」のような中身の無い返事が 1 つの仮説に入っている。「短い返事」に入れた「はい。でも帰るとやっぱり動画見ちゃって。」は、短い返事とは言いにくい。反例の `student-seiseki-2` の発話 21 も同じ形とは言えない。
- **H1・H5 から因果は言えない。** 分かるのは「講師の発話のあとに、相手の発話が続いた」順番までで、その問いが相手の話を増やしたとは言えない。夢の文は「あった」と書き、「まだ分からないこと」にも書いているが、読む側が因果に読みやすい。
- **確からしさは校正していない。** 夢自身の見立てで、当たる割合を測っていない。画面に出すなら、出所を明記し、引用の一致とは別に見せる。
- **「n 回のうち」は、記録に残った場面の中での数。** 記録に入るのは 1 回の面談につき場面 2 つと追跡の根拠だけで、場面を選んだのも AI。面談全体での出方の多さではない（夢も冒頭にそう書いた）。
- **追跡の判定が、台本の仕込みと違う面談が 1 本ある。** `student-seiseki-2` は、工程 4 の判定が「できた」、台本の仕込み（〔案〕。作り手はまだ確かめていない）は「一部」。英語の場面（発話 61〜62）で聞き返しが無いことを、工程 4 は「なぜ」の文に書いたが、引用には挙げなかった。記録には引用と前後の発話しか入らないので、夢はこの場面を反例に使えなかった。これは分析の側の出力を記録がそのまま受け継いだもの。
- **夢が欄の名前を取り違えた所が 1 か所。** `actions.md` で「記録の観察には」と書いた文は、記録では「その回の AI の読み（追跡の判定のなぜ）」の欄にある。
- **夢が指示に無いものを足した。** 4 つのファイルの 2 行目から、name・description・metadata の欄。metadata に「一字照合済み」とあるが、これは夢が自分で書いた言葉で、照合したのはアプリ。

指示（`engine/recorder.mts` の `dreamInstructions`）は、上の問題に合わせて直した。直した指示ではまだ夢を回していないので、効くかは分からない。
